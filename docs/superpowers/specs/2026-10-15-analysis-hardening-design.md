# 扫描判定、MCP 生命周期与发布验收加固

用户已批准按 2026-10-15 代码审查顺序实施：先两个 P1，再处理 MCP、验收和性能，补回归，保持 JDK 7/8 与规则泛化，三个项目复验后推送 GitHub。

## 设计

1. Python 不确定性按受影响的函数、表达式和路径传播。无关调用不能消除已确定违规；整个文件被丢弃时单独表示覆盖缺口，已确定违规仍优先。
2. Java 静态初始化、实例初始化和字段初始化纳入有序执行体。不能可靠建模的构造器关联或动态上下文明确未知，不伪造安全观察。
3. 完整单行的无效 JSON/RPC 返回错误后继续服务；超长帧仍可终止。报告先暂存，取消和最终发布有明确先后关系，正式文件与任务完成状态一致。
4. 验收强制真实 JDK 7、8 两个不同版本。统一入口执行原生编译、双 JVM 单元测试和最终 JAR 的 MCP 矩阵，记录制品摘要。
5. 调用图按类型、方法名、参数数量索引。共享单次扫描只读解析结果，各分析器保留独立状态和预算；不引入跨扫描缓存。

选择局部修复与单次扫描复用，控制替换解析框架、跨扫描缓存引入的兼容及维护成本。

## 验收与边界

- 保持真实 JDK 7/8 运行；不得引入 Java 8+ 运行 API。
- 不执行或修改三个目标应用；外部合同保持源码摘要绑定，UNKNOWN 不表示安全通过。
- P1 使用改名合成样例和 Scanner 公共入口验证受保护、违规、局部不支持、解析失败及无关函数隔离。
- 服务测试覆盖错误请求后的正常 ping，以及取消在生成/发布阶段的竞态；保留路径授权、不覆盖和符号链接防护。
- 性能回归验证候选工作量与结果等价，不用固定耗时作为唯一门禁。
- 三个项目双 JVM 重扫，核对三格式、UNKNOWN 分类、映射覆盖、目标工作区未修改；新 Codex 进程加载最终制品。
- 公开提交仅含扫描器、通用测试、文档与汇总；私有映射、目标源码/报告及演示文稿不在提交范围。
